## 3. Orchestration shape, validation layers, topology

### The three tiers

The orchestrator is this session.
It runs pre-flight, the wave loop, the gates, the merges, the spec edits, and the escalations, and it never implements.
It reads verdicts, unit logs, and core diffs only, to keep its context alive for the whole run.

Validators are fresh-context Opus subagents, one per unit, dispatched when the unit's implementer returns.
A validator is read-only and never fixes anything.

Implementers are one background agent per unit, launched through the harness's `Agent` tool, each in a worktree it creates itself with the commands in its unit block.

### The three validation layers

1. **Implementer self-check.** The worker runs its unit's acceptance command (worktree form) and records the real output before its closing commit.
2. **Per-unit validator.** A fresh Opus subagent first byte-compares every plan-verbatim file the unit created or edited against the custody canon (section 4.5), then independently reruns the acceptance command, walks every criterion with evidence, audits the diff against the ownership list, and returns `{verdict, criteria, notes}`.
3. **Orchestrator gate.** The orchestrator merges validated branches into `persona-seats` in the owning repo, reruns the unit's acceptance command from the plan text verbatim against the main checkout (`/tmp/persona-seats-loop/checks/uNN.sh`), runs the repo's gate, and advances only on green.

### Transport decision (BATCH lean, recorded with its reversal path)

Every unit takes the background-agent transport; none takes ringer.
This is a lean, not a forced move, and it is journaled at the execution approval as a BATCH take (under the pause knob it is surfaced inside that ask rather than auto-taken).
Reasons:

1. The claude-zai lane is unavailable (session instruction, confirmed by MODEL-NOTES 2026-09-30 and 2026-10-01), so ringer's flat-rate advantage is gone; its `claude` engine would run the same models at the same quota cost.
2. Every task ends with a plan-mandated `git add` and `git commit`, and ringer's `instructs_git_commit` lint hard-blocks specs that commit under worktrees.
3. U03 writes a deliverable outside git (`~/.config/jrit/personas/data-analyst.md` and its `.bak`), which a ringer worktree patch export cannot carry.
4. jrit-craft's gates read the jrit-personas checkout by sibling path and by `$HOME/repos/jrit/jrit-personas`, which a ringer task directory would not provide.

Cost: no scoreboard rows from this run.
The MODEL-NOTES receipts are the only durable model evidence, so they are mandatory at every gate (section 6.1, Step F).
Reversal path: re-route any single unit to a ringer manifest on the `claude` engine, rewriting its commit step into a patch export the orchestrator applies with `git am`; U03 is the one unit that cannot be reversed this way.

## 4. Hazard mitigations

### 4.1 Nested repos: LIVE on this host

`/home/jjrdar/repos/jrit` is itself a git repository (16 tracked files), and jrit-personas and jrit-craft are untracked nested directories inside it.
The harness's built-in `isolation: worktree` would snapshot that outer repo, so no implementer is launched with it.
Each implementer creates its own worktree with the explicit `git -C <repo> worktree add <path> -b <branch> persona-seats` command spelled out in its unit block, and works only inside that path.

Placement rule: every worktree is a sibling of the two main checkouts under `/home/jjrdar/repos/jrit/`, for example `/home/jjrdar/repos/jrit/jrit-craft-u02` and `/home/jjrdar/repos/jrit/jrit-personas-u05`.
For jrit-craft this is load-bearing, not cosmetic: `tests/regression-validators.sh` resolves the persona checker as `$ROOT/../jrit-personas/ci/check-persona-format.sh` and silently skips its negative case (a vacuous pass) when that path is absent.
The sibling worktrees show up as untracked directories in the outer repo; that is harmless, the outer repo is not driven, and the gate prunes them.

### 4.2 Path rewrite in the plan's commands (deviation)

The source plan's commands name the main checkouts: `cd ~/repos/jrit/<repo>` and `git -C ~/repos/jrit/<repo>`.
Run as written, a worker would edit and commit in the main checkout, the exact thing worktrees exist to prevent.
**Deviation:** in each unit's steps, acceptance command, and commit commands, the repo root is replaced by that unit's worktree path, and nothing else changes.
Each unit block in section 8.3 gives the rewritten forms, so no worker performs the substitution by hand.
Two path classes are never rewritten: `~/.config/jrit/personas/...` (U03's outside-git deliverable), and the `$HOME/repos/jrit/jrit-personas` reads inside jrit-craft's test scripts, which deliberately read the main checkout (4.3).
The orchestrator's gate rerun uses the plan text unchanged, against the main checkouts after merge.

### 4.3 Cross-repo gate dependency and the jrit-craft red window (resolved contradiction)

jrit-craft's `tests/task4-personas.sh` and `tests/task2-substrate.sh` read `$HOME/repos/jrit/jrit-personas` (the main checkout, absolute), and `tests/task4-personas.sh` line 35 runs jrit-personas's whole `ci/run-all.sh`.
`tests/regression-validators.sh` reads the sibling path.
So the orchestrator keeps the jrit-personas main checkout on `persona-seats` at all times and merges unit branches into it at each gate; U01 must be merged before any wave-2 jrit-craft gate runs, and U03 and U09 must be merged before U10 launches.
Never merge into either main checkout while a worker's or validator's jrit-craft check is running.

**Contradiction found and resolved.** The orchestrator brief named the jrit-craft gate as `bash ci/run-all.sh && bash tests/task4-personas.sh && bash tests/task6-craft-write.sh && python3 skills/craft-write/check-content.py --self-test` at every jrit-craft gate.
Verified on disk, `tests/task4-personas.sh` is red from U01's merge until U10 merges, by the source plan's design:

- After U01 merges and before U03: its line 17 runs the new checker over `kind:` personas (rejected), and line 35 runs jrit-personas's gate, which is red at structure check D.
- After U03 merges: its line 19 greps `^kind: audience$` on the migrated personas and fails with `FAIL: kind not audience: ...`; U10 is the task that changes that line.

The source plan agrees: Task 2's acceptance omits `task4-personas.sh`, and only the final gates in How to run include it.
**Resolution:** the wave-2 and wave-3 jrit-craft gates run `bash ci/run-all.sh && bash tests/task6-craft-write.sh && python3 skills/craft-write/check-content.py --self-test`, then run `bash tests/task4-personas.sh` and record its red as expected only when the failure line is `FAIL: kind not audience:` (any other failure is a real red).
The four-command gate is required green at wave 4.
Verified on 2026-10-08: jrit-craft's `ci/run-all.sh` runs structure-check, version-drift, secrets-scan, consumer-sweep, regression-validators, and plugin validate, and does not run `tests/task2-substrate.sh`, so U02's acceptance gate is meaningful inside the red window.

### 4.4 The jrit-personas red window

Between U01's merge and U03's merge, `bash ci/run-all.sh` in jrit-personas is red at structure check D by the source plan's design ("expected red: the checker rejects `kind` before the 13 personas are migrated").
The wave-1 gate therefore runs `bash tests/test_persona_format.sh`, `bash tests/test_references.sh`, and the U01 gate check, and runs `bash ci/structure-check.sh` expecting a failure at check D whose ERROR line carries `kind is retired`; checks A to C must still print their ok lines.
Nothing is pushed in the window, and the wave-2 gate is the first that requires `ci/run-all.sh` green.

### 4.5 Check custody collision (deviation, forced by the source plan)

The skill's custody rule says no unit may create or edit a check that judges it.
The source plan is test-first and has each unit create or edit its own check file verbatim from the plan: U01 `tests/test_persona_format.sh` and its fixtures, U02 a block in `tests/task6-craft-write.sh`, U05 to U08 `tests/test_skill_*.sh` (and U05, U06, U08 the eval files their tests require), U10 the edits to `tests/task4-personas.sh` and `tests/regression-validators.sh`.
**Deviation:** the plan text is the custody.
At pre-flight the orchestrator builds the custody canon (section 5.5), the exact expected bytes of every one of those files, read from the plan at its pinned commit `7fc16c6` and from the pre-run base commits, with a `SHA256SUMS` file recorded in the journal.
Every validator `cmp`s the worker's file against the canon before trusting any PASS and treats any divergence as fail, and the orchestrator reruns the acceptance command from the plan text at the gate.
U03, U04, and U09 author no check (their acceptance commands live in the plan), so their custody is clean; U04's persona is still canon-compared because H1 reads it.
A slip edit that changes a verbatim block changes a unit's produced contract or its check, so it is a STOP, and the canon is rebuilt after it.

### 4.6 The receipt helper runs `--ran` under dash (new hazard, found at compile)

`receipt.sh done --ran "<cmd>"` re-executes the command with `sh -c`, and `/bin/sh` on this host is dash.
U04's acceptance command uses process substitution, `diff <(awk ...)`, a bash-only construct.
Verified: `sh -c 'diff <(echo a) <(echo a)'` prints `Syntax error: "(" unexpected` and exits 2, which the helper would read as a failed check, routing a passing U04 to `agent:review` with exit 7.
**Mitigation:** every unit's acceptance command is written verbatim into `/tmp/persona-seats-loop/checks/uNN.sh` at pre-flight, and every `done` call passes `--ran "bash /tmp/persona-seats-loop/checks/uNN.sh"`.
The `--receipt` text names the plan line the check came from, so the receipt stays meaningful after `/tmp` is gone.
Record this as a SIGNAL line in MODEL-NOTES at the wave-1 gate (helper defect, not model).

### 4.7 Implementers and the reviewer conduct contract (deviation)

The orchestrator brief requires the reviewer conduct contract pasted verbatim into every implementer template as well as every validator template.
The contract bars writes outside the checkout, but the plan mandates some for implementers.
**Deviation:** the implementer template pastes the contract verbatim, reads "this repository checkout" as the worker's own worktree, and lists the only permitted outside writes: creating its worktree, appending to its own log under `/tmp/persona-seats-loop/logs/`, temp files the repo's own tests create and clean, U03's backup and one-line edit of `~/.config/jrit/personas/data-analyst.md`, and U10's `rm -rf "${TMPDIR:-/tmp}"/t2-checker-*`.

### 4.8 Commit attribution and resume-pointer staging (deviation)

The harness injects a `Co-Authored-By` line into commits unless a prompt forbids it, and Jeremy's standing rule forbids any co-author or agent attribution.
Every implementer prompt forbids it explicitly, every validator checks for it, and the orchestrator's own commits in this run (journal, merges, MODEL-NOTES) carry none either.
**Deviation:** each unit's closing commit stages and commits the plan's paths plus its resume pointer `docs/handoffs/2026-10-08.<slug>.resume.md` (in its own repo); the commit message stays byte-verbatim.
U10 makes two commits by design; its resume pointer rides in the first one, so the second (the one-line `seat-review.md` change) stays revertible on its own for Jeremy's H1 veto.

### 4.9 GNU-only `sed -i` (known deviation from the house rule)

The source plan's migration commands (Task 3 Step 3, Task 10 Step 6) and the README deliverable (Task 9 Step 3) use `sed -i` with no suffix, which is the GNU form.
The plan is ground truth and this host is WSL Linux, so workers run the commands as written; this is noted once as a deviation from the house no-GNU-flags rule.
The README one-liner is different: it is advice to readers on other machines.
It is flagged for Jeremy's H1 read (section 6.3), and changing it touches U09's acceptance grep, so it is his call and STOP-class if raised.
One tradeoff to name with it: the portable form `sed -i.bak` leaves a `.bak` beside each persona, and in `~/.config/jrit/personas/` that is a directory craft-write enumerates (the same hazard H4 cleans up).

### 4.10 Style rules bind human-read artifacts only (noted, not a deviation)

The source plan already narrows its sentence-per-line rule to human-read deliverables (docs, skills, doctypes, personas, README) and exempts machine-read run artifacts, which matches the skill's standing rule.
Workers and validators apply sentence-per-line to that set only; resume pointers, unit logs, gate check files, and structured output are exempt.
The em dash is banned everywhere, because both repos' structure checks scan `docs/` for it (jrit-personas check B, jrit-craft check G), and resume pointers land in `docs/handoffs/`.

### 6.2 Slip rules

A validator returns `spec-problem`, or the gate finds a defect that is not the worker's:

- **Small spec edit**: confined to a single unit or criterion, leaving unchanged what that unit is asked to produce, touching 15 or fewer lines of the source plan: edit the plan, commit it, relaunch that unit.
  BATCH, journaled with its reversal (`git revert` of the plan commit). `[gate:BATCH]`
- **Larger edit**, or one touching multiple units, a global constraint, a verbatim block, or a unit's produced contract: halt and ask.
  Rebuild the custody canon afterward if a verbatim block changed. `[gate:STOP]`
- **Design issue**, not a spec typo: record it in the journal for the downstream review, and carry it to the final human checkpoint with the advisory `/loop-review` findings.
  Do not fix it inside the wave.

## 7. Quota, interruption, and resume

The orchestrator cannot see the remaining quota, so the loop must be able to die at any moment without losing work.
Background agents are not a durable scheduler: if this session dies, the loop stops, and a fresh session resumes it.

### 7.1 Durable-state rules

- Run state lives on the claimed ticket.
  The `AGENT STATUS` receipt is posted on claim and at every gate, carrying branch, worktree path, validator verdict, and repair count.
- Every unit writes its resume pointer at `docs/handoffs/2026-10-08.<slug>.resume.md` in its own repo after its acceptance check passes and before its closing commit, and commits it.
- Every unit commits on its own branch before returning; a worker that returns without committing produced nothing durable.
- The journal is appended and committed at every gate, so a run that dies mid-chain still records every decision taken.
- The MODEL-NOTES receipt is committed in the ringer repo before each wave advances: the run checkpoints three repositories (jrit-personas, jrit-craft, ringer).
- `/tmp/persona-seats-loop/` is a cache: logs may be lost, and the canon and check files are rebuilt from section 5.5.
- **Git is reconciliation truth.** When a receipt or a resume pointer disagrees with a repository, believe the repository.

### 7.2 Reconciliation procedure (relaunch, never resume)

A fresh session picking up a dead run does this, in order:

1. Read this file, then the source plan, then `JOURNAL` (the newest `docs/reviews/*persona-seats-batch-review.md`) for the unit-to-issue map, the two pre-run bases, the session id of the dead run, and the last gate recorded.
2. Read the newest resume pointer naming each unit, in both repos: `ls -t docs/handoffs/2026-10-08.*.resume.md` in jrit-personas and in jrit-craft.
3. Find the killed unit: `bash "$HELPER" next-eligible "$SID"` (its stale-working sweep surfaces a dead session's ticket), or reclaim a known one with `bash "$HELPER" claim <num> "$SID" --reclaim`.
4. Read that ticket's `AGENT STATUS` receipts.
5. Check git in both repos and let it overrule everything: `git -C <repo> branch --show-current` (both must be `persona-seats`), `git -C <repo> log --oneline <pre-run base>..persona-seats`, `git -C <repo> branch --list 'loop/persona-seats/*'`, `git -C <repo> worktree list`, `git -C <repo> status --porcelain`.
   A unit whose commit is already merged into `persona-seats` is done, whatever its ticket says; close it through the helper with its gate check.
6. Check the ringer repo for a receipt owed by the last gate: `git -C /home/jjrdar/repos/ringer status --porcelain docs/MODEL-NOTES.md`; commit it before anything else.
7. Check the user-tier file state: `test -f ~/.config/jrit/personas/data-analyst.md.bak` and `sed -n 3p ~/.config/jrit/personas/data-analyst.md`.
   A half-done U03 is safe to relaunch: the backup guard never overwrites an existing `.bak`, and the `sed` is idempotent.

9. Remove every half-done unit's worktree and branch (`git -C <repo> worktree remove --force <path>`, `git -C <repo> branch -D loop/persona-seats/uNN`) and **relaunch it from scratch** from its template; never resume a half-done unit mid-flight.
