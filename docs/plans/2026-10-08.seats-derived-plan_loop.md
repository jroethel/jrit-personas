## 3. Orchestration shape, validation layers, topology

### The three tiers

The orchestrator is this session.
It runs pre-flight, the wave loop, the gates, the merges, the spec edits, and the escalations, and it never implements.
It reads verdicts, unit logs, and core diffs only, to keep its context alive for the whole run.

Validators are fresh-context Opus subagents, one per unit, dispatched when the unit's implementer returns.
A validator is read-only and never fixes anything.

Implementers are one background agent per unit, launched through the harness's `Agent` tool, each in a worktree it creates itself with the commands in its unit block.

### The three validation layers

1. **Implementer self-check.** The worker runs its unit's acceptance command (worktree form), records the plan's expected-fail output before implementing and the real final output after, and only then makes its closing commit.
2. **Per-unit validator.** A fresh Opus subagent first byte-compares every plan-verbatim file or block the unit created or edited against the custody canon (section 4.5), then independently reruns the acceptance command, walks every criterion with evidence, parses every edited frontmatter as YAML, audits the diff against the ownership list, and returns `{verdict, criteria, notes}`.
3. **Orchestrator gate.** The orchestrator merges validated branches into `persona-seats` in the owning repo, reruns the unit's acceptance command from the plan text verbatim against the main checkout (`bash /tmp/seats-derived-loop/checks/uNN.sh`), runs the wave's gate table (section 6.1, Step D), and advances only on green.

### Transport decision (journal E2, BATCH, cited not re-decided)

Every unit takes the background-agent transport; none takes ringer.
Ringer is present on this host, and this is a lean recorded as BATCH in journal E2, with these four reasons:

1. The owner restricted workers to opus, sonnet, and haiku, so ringer's flat-rate lane is out, and its `claude` engine would run the same models at the same quota cost.
2. Every task ends with a plan-mandated `git add` and `git commit`, and ringer's `instructs_git_commit` lint hard-blocks specs that commit under worktrees.
3. Task 2 writes a deliverable outside git (`~/.config/jrit/personas/data-analyst.md`), which a ringer worktree patch export cannot carry.
4. jrit-craft's gates read the jrit-personas main checkout by absolute path (`$HOME/repos/jrit/jrit-personas`) and by sibling path (`../jrit-personas`), which a ringer task directory would not provide.

Cost: no scoreboard rows from this run, so the MODEL-NOTES receipts are the only durable model evidence and are mandatory at every gate (section 6.1, Step F).
Reversal path (from E2): re-route any single unit to a ringer manifest on the `claude` engine with its commit step rewritten as a patch export; U02 cannot be reversed this way (outside-git deliverable).

## 4. Hazard mitigations

### 4.1 Nested repos: LIVE on this host

`/home/jjrdar/repos/jrit` is itself a git repository, and jrit-personas and jrit-craft are untracked nested directories inside it.
The harness's built-in `isolation: worktree` would snapshot that outer repo, so no implementer is ever launched with it.
Each implementer creates its own worktree with the explicit `git -C <repo> worktree add <path> -b <branch> persona-seats` command spelled out in its unit block, and works only inside that path.

Placement rule: every worktree is a sibling of the two main checkouts under `/home/jjrdar/repos/jrit/`: `jrit-personas-u01` to `jrit-personas-u07`, and `jrit-craft-u08`.
For jrit-craft this is load-bearing, not cosmetic: `tests/regression-validators.sh` resolves the persona checker as `$ROOT/../jrit-personas/ci/check-persona-format.sh` and silently skips its negative case (a vacuous pass) when that path is absent.
The sibling worktrees show up as untracked directories in the outer repo; that is harmless, the outer repo is not driven, and the gate prunes them.

### 4.2 Path rewrite in the plan's commands (deviation)

The source plan's commands name the main checkouts: `cd ~/repos/jrit/<repo>` and `git -C ~/repos/jrit/<repo>`.
Run as written, a worker would edit and commit in the main checkout, the exact thing worktrees exist to prevent.
**Deviation:** in each unit's steps, acceptance command, and commit commands, the repo root is replaced by that unit's worktree path, and nothing else changes.
Each unit block in section 8.3 gives the rewritten forms, so no worker performs the substitution by hand.
Two path classes are never rewritten: `~/.config/jrit/personas/...` (U02's outside-git deliverable and every check that reads it), and the `$HOME/repos/jrit/jrit-personas` reads inside jrit-craft's test scripts, which deliberately read the main checkout (4.3).
The orchestrator's gate rerun uses the plan text unchanged, against the main checkouts after merge.

### 4.5 Check custody collision (deviation, forced by the source plan)

The skill's custody rule says no unit may create or edit a check that judges it.
The source plan is test-first and has U01, U03, U04, U05, U06, and U08 each rewrite or edit the very test that judges them, verbatim from the plan.
**Deviation:** the plan text is the custody.
At pre-flight the orchestrator builds the custody canon (section 5.5): the exact expected bytes of every plan-verbatim or mechanically derived file each unit produces, read from the plan at its pinned commit `2c7b375` and from the two pre-run base commits, with a `SHA256SUMS` file recorded in the journal.
The canon covers 56 files: 50 whole files every validator `cmp`s, and 6 blocks (`*.block.*`) a validator checks are contained verbatim in the target file.
Every validator runs the canon comparison before trusting any PASS and treats any divergence as fail, and the orchestrator reruns the acceptance command from the plan text at the gate.
U02 and U07 author no check (their acceptance commands live in the plan), so their custody is clean; their deliverables are still canon-compared.
A slip edit that changes a verbatim block changes a unit's produced contract or its check, so it is a STOP, and the canon is rebuilt after it.

### 4.6 The receipt helper runs `--ran` under dash (carried forward, defensive this run)

`receipt.sh done --ran "<cmd>"` re-executes the command with `sh -c`, and `/bin/sh` on this host is dash (MODEL-NOTES 2026-10-08 SIGNAL).
All eight of this run's acceptance commands pass `sh -n` under dash, so none is bash-only this time; the wrapper is kept anyway because it costs nothing and keeps one rule for every run.
**Mitigation:** every unit's acceptance command is written verbatim into `/tmp/seats-derived-loop/checks/uNN.sh` at pre-flight, and every `done` call passes `--ran "bash /tmp/seats-derived-loop/checks/uNN.sh"`.
The `--receipt` text names the plan line the check came from, so the receipt stays meaningful after `/tmp` is gone.
No new MODEL-NOTES signal is owed for it; the 2026-10-08 line already records the defect.

## 7. Quota, interruption, and resume

The orchestrator cannot see the remaining quota, so the loop must be able to die at any moment without losing work.
Background agents are not a durable scheduler: if this session dies, the loop stops, and a fresh session resumes it.

### 7.1 Durable-state rules

- Run state lives on the claimed ticket.
  The `AGENT STATUS` receipt is posted on claim and at every gate, carrying branch, worktree path, validator verdict, and repair count.
- Every unit writes its resume pointer at `docs/handoffs/2026-10-08.<slug>.resume.md` in its own repo after its acceptance check passes and before its closing commit, and commits it.
- Every unit commits on its own branch before returning; a worker that returns without committing produced nothing durable.
- The journal is appended and committed at every gate, so a run that dies mid-chain still records every decision taken.
- The MODEL-NOTES receipt is committed in the ringer repo before each wave advances: the run checkpoints three repositories (jrit-personas, jrit-craft, ringer).
- `/tmp/seats-derived-loop/` is a cache: logs may be lost, and the plan copy, canon, and check files are rebuilt from section 5.5.
- **Git is reconciliation truth.** When a receipt or a resume pointer disagrees with a repository, believe the repository.

### 7.2 Reconciliation procedure (relaunch, never resume)

A fresh session picking up a dead run does this, in order:

1. Read this file, then the source plan, then `JOURNAL` (the newest `docs/reviews/*seats-derived-batch-review.md`) for the unit-to-issue map, the two pre-run bases, the `.bak` hash, the session id of the dead run, and the last gate recorded.

4. Read that ticket's `AGENT STATUS` receipts.
5. Check git in both repos and let it overrule everything: `git -C <repo> branch --show-current` (both must be `persona-seats`), `git -C <repo> log --oneline <pre-run base>..persona-seats`, `git -C <repo> branch --list 'loop/seats-derived/*'`, `git -C <repo> worktree list`, `git -C <repo> status --porcelain`.
