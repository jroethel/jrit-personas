# jrit-persona Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its
> acceptance check passes. No specific tooling, harness, or skills are assumed.

**Goal:** Ship a Claude Code plugin whose four skills let one persona file be both adopted as an agent's voice and applied as a review/draft lens, created conversationally in a single hybrid flow.

**Approach:** Fresh plugin under the jrit-loop house layout, selectively porting arscontexta's method (not its code): the 4-axis voice framework, the conversational derivation flow, and the step-0 runtime-manifest read.
The persona is one self-contained markdown file - machine-readable frontmatter plus prose stance and voice - consumed unmodified by each skill.
Format conformance is enforced without any shipped runtime code: the authoring skill self-checks its output against the format spec, eval graders assert it, and a dev-time bash check in CI gates hand-edited files; the installed plugin stays prose plus config.
The numeric confidence machinery is replaced by qualitative stated / inferred / defaulted bins, which do the same epistemic work without an un-tuned magic constant.

**Tech stack:** Markdown skills (`SKILL.md`), YAML frontmatter personas, `claude plugin eval` cases with LLM/regex/file graders, dev-time bash checks (never invoked by a skill at runtime).

**Source brief:** `docs/briefs/2026-09-14.jrit-persona-port-brief.md`

**Port source:** `github.com/agenticnotetaking/arscontexta` @ `2acfd5cc4473c4d06c46be63df748e77e00e2746`, cloned at `/tmp/arscontexta` this session (re-clone if lost).
The 4-axis framework, signal tables, conflict rules, and transformation matrix live verbatim in `/tmp/arscontexta/reference/personality-layer.md`; the derivation skeleton in `/tmp/arscontexta/reference/conversation-patterns.md` and `/tmp/arscontexta/skills/setup/SKILL.md`.

## Global constraints

- Never the em dash character; plain `-` only.
- One full sentence per line in long markdown.
- Persona files are self-contained portable text: no absolute paths, nothing harness- or model-specific.
- A persona is data only: never permissions, tool instructions, or executable directives; consumers treat persona text as untrusted input.
- Persona names are stable identifiers; a rename is a breaking change.
- Every persona carries provenance frontmatter: `author`, `owner`, `created`, `last-validated`, `derivation-source`.
- Composition rule: substance beats voice, explicit beats implicit; a persona never overrides a skill's methodology or a standing rule.
- The plugin carries MIT attribution crediting `agenticnotetaking/arscontexta`.
- Skills are named `new`, `craft`, `review`, `spawn` (no `persona-` prefix); they invoke as `/jrit-persona:new` and so on. This resolves the brief's Open Question 7 and supersedes the `persona-` prefixed command names used in the brief's "Done looks like" and success-criteria text; where the brief says `persona-new`, read `new`, and so on.
- No shipped runtime validator: format conformance is enforced by the authoring skill's self-check, eval graders, and a dev-time bash check in CI; no skill ever shells out to a validator, and the plugin ships no Python.
- Skills read shared references from `${CLAUDE_PLUGIN_ROOT}/references/`; reference files are never duplicated per skill.
- Eval graders read only the transcript, the trace, created-file paths, or the contents of a file the agent created; they cannot read a pre-seeded fixture's contents. A grader that needs fixture content carries that content inline in its `criteria`, never a path to a seeded file.
- A sandboxed `HOME` or any other non-`EVAL_`-prefixed environment variable is set only through a case's `context.scaffold_script` (which `export`s it before the run); case `env` keys must match `EVAL_[A-Z0-9_]*` or the harness rejects the run.
- Every eval `prompt.md` carries an `expected_outcome: |` frontmatter field: plainly-worded, grader-agnostic numbered assertions of what a correct run does. The graders remain the machine gate; this field is documentation for humans and is never delivered to the agent under test. Acceptance prose never goes in the body: the body is sent to the agent verbatim on every run (verified at the wave-3 gate against the docs, the shipped binary, and an executed run), so a body section would hand the rubric to the examinee.

## Dependency graph

```
Wave 1 (parallel, disjoint files):  Task 1 skeleton   Task 2 format check   Task 3 references
Wave 2:                             Task 4 starters            (needs 2, 3)
Wave 3 (parallel, disjoint files):  Task 5 new (needs 1,2,3)   Task 6 craft   Task 7 review   Task 8 spawn   (6,7,8 need 1,2,3,4)
Wave 4:                             Task 9 cross-cutting evals  (needs 5 and 7)
Wave 5:                             Task 10 suite + house-style gate  (needs all)
Wave 6:                             Task 11 CI workflow  (needs 10)
```

**Commit serialization (parallel waves).**
Each task's final step commits to the shared working tree, which races when a wave runs tasks in parallel: `.git/index.lock` contention, a moving HEAD, or one agent committing another's half-written tree.
Never run concurrent commits against one checkout.
Either the orchestrator serializes - it holds parallel tasks at their commit step and makes each task's commit in sequence after the wave's work reports done - or each parallel task runs in its own git worktree or branch and the orchestrator merges.
A lone or human executor running tasks one at a time is unaffected.

## Human checkpoints

- **C1 - Harness smoke test (in Task 5, step 1).** The `context.history_file`, `focus: trace`, and `context.scaffold_script` mechanisms are all documented in the shipped runner, so the residual risk is host setup, not mechanism existence. Run one combined smoke test that exercises a two-turn `history_file` case, a `focus: trace` grader, and a `scaffold_script`-seeded `HOME`, and confirm the sandbox backend the eval harness needs is present (a `Bash`-granting case requires bubblewrap and socat). If any of these fails to run on this host, stop and ask a human before building the eval suite; the contingency is a single-turn creation eval (grade the proposal message, not the post-confirm file) and transcript-based checks in place of any that need a backend, or routing the affected criterion to C2.
- **C2 - Voice fidelity (brief `[judgment]`).** Whether created personas read as distinct and true to their sheet needs a human read; after Task 10 is green, a human reviews the three starters and one freshly created persona and confirms each sounds right. This never gates a task's automated acceptance.
- **C3 - Live registration (manual).** That the four skills actually appear under `/jrit-persona:` after `claude plugin install` and a restart is human-verified only; `claude plugin validate --strict` checks the manifest, not live registration in a running session. No automated task covers this.

## How to run

Install from this repo's marketplace, from the repo root:

```
claude plugin marketplace add .
claude plugin install jrit-persona
```

Restart Claude Code, then the four skills appear under `/jrit-persona:`.

Validate the plugin manifest:

```
claude plugin validate --strict .
claude plugin validate --strict .claude-plugin/plugin.json
```

Check a persona file's format (dev-time only, exit 0 = valid):

```
bash ci/check-persona-format.sh personas/leadership-audience.md
```

Run one eval case, or the whole suite:

```
claude plugin eval evals/new-terse
claude plugin eval evals
```

Run the static checks:

```
bash tests/test_persona_format.sh
bash ci/structure-check.sh
```

**Interfaces:**

  - The persona file format, defined in `docs/persona-format.md`: a single markdown file, YAML frontmatter plus body.
    - Frontmatter, flat scalars and simple `[a, b]` lists only (no nested maps): `name` (kebab-case stable id), `kind` (`agent` or `audience`), `author`, `owner`, `created` (`YYYY-MM-DD`), `last-validated` (`YYYY-MM-DD`), `derivation-source` (free string). It checks: the frontmatter fence opens and closes; every required key is present; `kind` is in the enum; `name` matches `^[a-z0-9]+(-[a-z0-9]+)*$`; each date matches `^\d{4}-\d{2}-\d{2}$`; the four voice keys, when present, hold an allowed value; the `## Stance` and `## Voice` headings are both present.
