# Persona Seats Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its acceptance check passes. No specific tooling, harness, or skills are assumed.

**Goal:** Replace the persona `kind` field with a `seats` list (creator, reviewer, audience) so one persona file models one person in every seat they sit in, define jargon tolerance in writing, ship the `change-management-prosci` persona, and add the `training-material` and `team-update` doctypes to jrit-craft.

**Approach:** Land the contract first: the format doc, the dev-time checker, and its fixtures define `seats`, the optional `## As <seat>` sections, the audience-only keys, and the jargon definitions.
Then, in parallel, migrate every `kind:` file mechanically, add the new persona, and align the four skills to the contract, each skill with its own anchor test.
jrit-craft gets two changes in its own commits: the two doctypes (after Task 1, because jrit-craft's gate runs the jrit-personas checker) and the move of its persona checks and eval seeds from `kind` to `seats` (after jrit-personas is green).

**Tech stack:** Markdown skills (`SKILL.md`) and doctype files, flat YAML-frontmatter persona files, dev-time bash checks using `grep`/`sed` only, the existing jrit-craft `check-content.py` self-test, `claude plugin validate` and `claude plugin eval`.

**Source brief:** `docs/briefs/2026-10-08.persona-seats-brief.md` (in `~/repos/jrit/jrit-personas`)

## Global constraints

- Never use the em dash character (U+2014); use a plain `-`.
- One full sentence per line in human-read Markdown deliverables (docs, skills, doctypes, personas, README); machine-read run artifacts (eval results, logs) are exempt.
- Plain commit messages: no `Co-Authored-By` line, no agent or tool attribution of any kind.
- Never hand-edit a CHANGELOG or any generated file (neither repo has one today; do not create one).
- Persona files are portable: no absolute paths, nothing harness- or model-specific.
- `banned-jargon: [elephant]` in `personas/change-management-prosci.md` is a deliberate placeholder; do not change it.
- Do not push either repo; pushing and updating installed plugins are human checkpoints.
- jrit-personas root is `~/repos/jrit/jrit-personas`; jrit-craft root is `~/repos/jrit/jrit-craft`; every git command names its repo with `git -C <repo>`.
- All work happens on a branch named `persona-seats` in each repo: jrit-personas already has it (the brief and this plan were committed there), and jrit-craft gets it in How to run before Task 1.
- Commit only your own paths: `git -C <repo> add <paths>` then `git -C <repo> commit -m "<msg>" -- <paths>`, so a parallel task's staged files never ride along.
- Parallel tasks in one repo stage and commit one at a time; a `git add` or `git commit` that meets `.git/index.lock` waits for the other git command to finish and retries.
- The brief's migration is mechanical: `kind: agent` becomes `seats: [creator]`, `kind: audience` becomes `seats: [audience]`; no persona body is edited during migration.
- jrit-personas version becomes `0.2.0`; jrit-craft version becomes `0.2.0` (minor bump from `0.1.0`); neither `marketplace.json` carries a version.

```bash
# reject <fixture-basename> <phrase only the intended rule prints>
# The ` in <file>` suffix is stripped before matching, so a fixture name can never satisfy the phrase.
reject() {
  local out
  if out=$(bash "$CHECK" "$FX/$1.md" 2>&1); then
    fail "$1.md should be rejected (nonzero exit)"
  fi
  printf '%s\n' "$out" | grep -q '^ERROR:' || fail "$1.md rejection must print an ERROR: line (got: $out)"
  printf '%s\n' "$out" | sed 's/ in [^ ]*$//' | grep -qF -- "$2" || fail "$1.md rejection must say '$2' (got: $out)"
```

```
## Seats

`seats` names the seats this one person sits in, as a simple list drawn from `creator`, `reviewer`, and `audience`; at least one seat is required.

- `creator`: the persona writes deliverables in its own voice.
- `reviewer`: the persona approves material other people drafted.
- `audience`: the persona reads material shaped for it.

Stance and Voice are shared across every seat: one identity, one voice.
Each seat may add an optional `## As <seat>` section holding only what that seat adds; a section for a seat not listed in `seats` is a format error.
The persona carries no severity: whoever runs a review rates each finding by its own rules, the persona never gates, and the human decides.
The reviewer seat lists what this person looks at; it never overrides a skill's methodology or a standing rule, and substance beats voice still holds.

`seats` replaces the retired `kind` key, and a file that still carries `kind` fails the format check.
Migration is mechanical: `kind: agent` becomes `seats: [creator]`, and `kind: audience` becomes `seats: [audience]`; seat sections are optional, so no body edit is required.

## Jargon

`jargon-tolerance`, `banned-jargon`, and `time-budget` belong to the audience seat, and the format check rejects them when `audience` is not in `seats`.
Creator and reviewer jargon is never a persona field: it always comes from the audience of the material.

- Jargon is any term this reader would need explained to follow the sentence: insider acronyms, method and framework names, system, tool, object, and field names, and team shorthand.
  Whether a term is jargon depends on the reader, not the term.
- `low`: every jargon term is replaced with plain words or defined in plain words at first use; no undefined acronyms.
- `medium`: terms native to the reader's own field are fine undefined; terms from other fields are defined at first use.
- `high`: specialist terms from the reader's field and adjacent fields are used freely.
- `banned-jargon`: terms never used, even when defined, and never swapped for a synonym that carries the same jargon meaning.

When `jargon-tolerance` is absent, no tolerance level is judged and none is inferred: only `banned-jargon` and plain clarity apply.
```
