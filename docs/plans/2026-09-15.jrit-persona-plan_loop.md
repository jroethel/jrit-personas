## 1. What this file is

This file is the orchestration plan compiled from `docs/plans/2026-09-15.jrit-persona-plan.md` by the loop-drive skill's drive-compile dispatch.
It turns a human-paced plan (open a session, paste a prompt, review, repeat) into a plan one frontier-model orchestrator session executes autonomously across six waves and eleven units.

The source plan is also the spec artifact and stays ground truth.
Where this file and the source plan disagree on what a unit must produce, the source plan wins, and the disagreement is a spec problem to route to the orchestrator rather than a license to improvise.
The deviations in section 4 are the only intentional departures, and each one is named there.

## 3. Orchestration shape, validation layers, topology

### The three tiers

The orchestrator is this session. It runs the wave loop, the gates, the merges, the spec edits, and the escalations, and it never implements.
It reads verdicts, logs, and core diffs only, to keep its context alive for the whole run.

Validators are fresh-context Opus subagents, one per unit, dispatched after the unit reports.
A validator never fixes anything.

Implementers are one worker per unit: a ringer manifest task for U01, U02, U03, U04, U11, and a background agent for U05 through U10.

### The three validation layers

1. **Implementer self-check.** The unit runs its own acceptance check from the source plan and must show the output. For ringer units this is the task's `check`, which ringer runs and retries once. For background-agent units it is the command named in the unit's Acceptance check line, run by the implementer before it commits.
2. **Per-unit validator.** A fresh Opus subagent independently re-runs the acceptance check against the artifacts, walks the criteria one at a time with evidence, audits the diff against the ownership list, and returns `{verdict, criteria, notes}`. It reads the diff and the executed output, never the implementer's narrative.
3. **Orchestrator gate.** The orchestrator reads all verdicts, merges passing work onto the integration branch, runs the full offline suite there, and advances only on green.

## 4. Hazard mitigations

### 4.1 Commit serialization becomes per-unit worktrees (deviation)

The source plan's "Commit serialization (parallel waves)" section names the hazard and offers two resolutions: orchestrator-serialized commits, or per-unit worktrees with orchestrator merges.
**This run takes the worktree branch of that choice, for every unit on both transports, including the single-unit waves.**
Ringer units get isolation from run-level `"worktrees": true`; background-agent units create their own worktree with an explicit command spelled out in their prompt.
No worker ever runs `git commit` against `/home/jjrdar/repos/jrit/jrit-personas` itself, and no worker runs `git push`.
This is a deviation only in the sense that it settles a choice the source plan left open; the plan's own words authorize it.

### 4.2 Nested repos: does not apply

There is no outer git repository above `/home/jjrdar/repos/jrit/jrit-personas`.
Verified this session: `git -C /home/jjrdar/repos/jrit rev-parse --show-toplevel` returns `fatal: not a git repository`.
The harness worktree-isolation footgun (snapshotting the wrong repo) therefore cannot fire on this host, and background-agent implementers may create their worktree against this repo directly.
The explicit `git -C <repo> worktree add` form is still used in every prompt, because it is unambiguous and costs nothing.

### 4.3 Check custody

No unit's acceptance-check script may be edited by a worker that the check judges, and a worker diff that touches a check file is an automatic scope violation, not something to resolve at the gate.

Four units author the very script that gates them, which is the METR reward-hacking surface.
Each gets a specific mitigation, and each mitigation is written into that unit's validator prompt:

- **U02** writes `tests/test_persona_format.sh` and is gated by it. The source plan gives that file verbatim, so the orchestrator owns the canonical text. The ringer `check` asserts byte identity of the worker's copy against the plan block (`git hash-object` comparison against an orchestrator-held copy outside the worktree) before it runs the test. The validator independently re-runs the test AND judges `ci/check-persona-format.sh` against the Produces contract clause by clause: fence open and close, every required key, `kind` enum, `name` regex, both date regexes, the four voice-key enums, and both body headings. A check script that exits 0 unconditionally, or that only greps for one key, is a fail even when the test passes.
- **U03** writes `tests/test_references.sh` and is gated by it, and the plan gives that file verbatim too. Same byte-identity custody assertion, same independent rerun, and the validator additionally judges whether `references/voice-framework.md` actually carries the four axes, the signal table, the three conflict rules, the transformation matrix, and the three qualitative bins, rather than merely containing the anchor strings the test greps for.
- **U10** writes `ci/structure-check.sh` and `ci/run-all.sh` and is gated by `bash ci/run-all.sh`. The validator must prove non-vacuity by mutation: plant an em dash in a scratch copy of a shipped markdown file and show the checker fails, plant a `/home/` path in a scratch persona copy and show it fails, then restore. A checker that passes a deliberately broken tree is a fail.
- **U11** writes `.github/workflows/ci.yml` and is gated by a grep against it. The criterion is objective enough that the validator's independent rerun plus a read of the file suffices.

U04 is gated by `ci/check-persona-format.sh`, authored by U02 in an earlier wave, so its custody is clean.
U05 through U09 are gated by `claude plugin eval` over graders they author; the graders are LLM judgments against a fixed rubric, and every one of those units ships a negative-control case whose purpose is to fail if the skill ignores the persona.
Each of those validators re-runs the eval independently and reads the grader criteria for question-begging (a grader that asserts only that a file exists where the plan asked for substance is a spec problem, reported as such).

### 4.4 Ringer transport footguns

- **Deliverable loss on a passing worktree.** A passing ringer task's worktree is deleted and its commits die with it. Every ringer task's `check` therefore exports the unit's work as a patch to a path outside the worktree before it exits: `git format-patch <base-sha>..HEAD --stdout > "$PATCH_OUT/<key>.patch"`, and `expect_files` names that patch. The orchestrator applies it with `git am` onto the integration branch, which preserves the source plan's verbatim commit message and adds no attribution line. This is the pattern proven in the 2026-09-09 and 2026-09-13 runs recorded in the ringer MODEL-NOTES.
- **Gitignored outputs.** This build produces no build directory and no gitignored artifact, so the explicit `cp`-out step is not needed. If a unit ever produces one, the check must copy it out explicitly, because `git add -A` will not stage it.
- **Check timeout.** `CHECK_TIMEOUT_S = 60` is hardcoded at `ringer.py:55` (verified this session). Every ringer unit's check in this run is a fast offline command (bash greps, a bash test script, `claude plugin validate --strict`, a YAML parse) plus the patch export, comfortably inside that ceiling. This constant is also the transport driver for U05 through U10; see 4.5.
- **Engine staggering.** The stagger rule is an OpenCode sqlite-contention issue. This run uses only the `claude-zai` engine on ringer, so `max_parallel: 3` in wave 1 needs no stagger.

### 4.5 Why U05 through U10 cannot take the ringer transport

Their acceptance checks are `claude plugin eval` runs, which are live authenticated agentic runs against the host's `claude` login and take minutes per case.
Two independent reasons put them on the background-agent transport, and either alone is sufficient:

1. **Verified.** Ringer's check ceiling is 60 seconds (`ringer.py:55`). A `claude plugin eval evals` suite run is far longer. The 2026-09-13 MODEL-NOTES entry for `u04fix` records exactly this failure mode: TIMEOUT x2 on work that was correct, because a 75-second check cannot run inside a 60-second ceiling.
2. **Inferred, not verified.** A ringer worker on the `claude-zai` engine runs the `claude` binary against z.ai credentials, so a `claude plugin eval` nested inside it would plausibly inherit that environment and grade against GLM rather than the host's authenticated login, silently invalidating the eval. I did not verify the engine's environment handling: the local `ringer.py` no longer carries the engine definitions inline and reports itself 17 commits behind a diverged origin. Treat reason 2 as a supporting argument only; reason 1 is the one that decides.

U05 additionally needs mid-flight continuation (iterate the SKILL.md until both eval cases pass), and U10 needs cross-file repair authority, both of which are background-agent properties.

### 4.6 Per-worktree environments

This build has no venv, no `poetry install`, and no dependency install step: it is markdown, JSON, YAML, and bash, checked by `claude` and `bash`.
The per-worktree environment hazard is nil here, and no install step is added to any prompt.
The one environment dependency is the `claude` binary on `PATH`, which is host-level and travels into every worktree.

### 4.7 Shared append-only state: none in the source plan (noted, not a deviation)

The source plan defines no shared run log, no shared checklist, and no file that every task appends to.
The only two multi-unit surfaces are `docs/handoffs/`, where each unit writes exactly one uniquely named resume pointer, and `docs/reviews/`, which the orchestrator alone owns.
Both are already one-file-per-unit or single-owner, so the usual shared-append-to-per-unit conversion has nothing to convert.

Per-unit worker logs for the orchestrator's watch points live **outside** the repository, at `/tmp/jrit-persona-loop/logs/unit-NN.md`, so they never enter a diff, never conflict at a merge, and never pollute the tree the house-style gate scans.

### 4.8 Disjoint files within a wave

Wave 1's three units touch disjoint paths by construction (U01 owns `.claude-plugin/`, `NOTICE`, `README.md`; U02 owns `docs/persona-format.md`, `ci/check-persona-format.sh`, `tests/test_persona_format.sh`, `tests/fixtures/`; U03 owns `references/`, `tests/test_references.sh`).
U02's source-plan commit line stages the broad path `tests/`, and U03's stages the narrow `tests/test_references.sh`; under per-unit worktrees these cannot collide, and at merge time the file sets are disjoint.
Wave 3's four units own four disjoint skill directories and eight disjoint eval directories.
A merge conflict at any gate is therefore a scope violation to attribute and report, never something to quietly resolve.

### 4.9 Resume-pointer staging (deviation)

The source plan's commit steps are given verbatim and their `git add` lines do not mention `docs/handoffs/`.
Every unit must also commit its resume pointer in its closing commit.
**Deviation:** each unit's closing commit stages the source plan's paths **plus** `docs/handoffs/2026-09-15.<unit-slug>.resume.md`, while the commit message stays byte-verbatim as the source plan gives it.
No co-author line, no attribution line, no trailer of any kind is added to any commit in this run.

### 4.10 U10's repair authority (deviation)

The source plan's Task 10 steps 3 and 4 tell the executor to fix house-style and eval failures "in the owning file", which are files other units authored, while Task 10's exclusive ownership list names only `ci/structure-check.sh` and `ci/run-all.sh`.
**Deviation:** U10's ownership list is those two files plus a bounded repair allowance over already-merged files from U01 through U09.
Every repair outside `ci/` must be itemized in U10's structured output with the file, the failing check, and the one-line fix.
An unlisted edit outside `ci/` is a scope violation.
U10 may not edit `tests/test_persona_format.sh`, `tests/test_references.sh`, or `ci/check-persona-format.sh`, because those are checks that gate earlier units; a defect found in one of them is reported to the orchestrator as a spec problem, not repaired by U10.

### 4.11 Human checkpoint C1 moves to the orchestrator (deviation)

Source plan Task 5 step 1 is the C1 harness smoke test, executed by the task's implementer.
**Deviation:** the orchestrator runs C1 itself at the **entry to wave 3**, before launching any wave-3 implementer.
Rationale: C1 is a STOP-class gate whose failure invalidates the entire eval strategy for U05 through U10, so it must halt the run before four parallel workers spend quota on an unbuildable premise.
U05's implementer prompt drops step 1 and receives the smoke-test results as given facts.
C1's procedure, pass condition, and failure handling are in section 6.
